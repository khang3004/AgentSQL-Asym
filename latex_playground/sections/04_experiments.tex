\section{Experiments}
\label{sec:experiments}

\subsection{Experimental Setup}

\subsubsection{Benchmark}
We evaluate AgentSQL on the \highlight{BIRD Mini-Dev} benchmark \parencite{li2024can}, a curated subset of the full BIRD dataset designed for rapid iterative development. The evaluation subset ($N = 10$) is drawn from the \texttt{debit\_card\_specializing} domain, featuring complex financial queries involving multi-table joins, date range filtering, segment-level aggregation, and inter-segment comparison.

\subsubsection{Model Configuration}
The asymmetric model allocation is as follows:
\begin{itemize}
    \item \textbf{Generator \& Reflector}: \texttt{meta-llama/llama-4-scout-17b-16e-instruct} via Groq API ($T = 0.0$, deterministic decoding).
    \item \textbf{Resilient Critic}: \texttt{gemini-2.5-flash} via Google AI ($T = 0.0$).
    \item \textbf{Embedding Model}: \texttt{BAAI/bge-small-en-v1.5} for CHESS query encoding.
    \item \textbf{CHESS Top-$k$}: $k = 3$ with oversampling factor $\times 10$.
\end{itemize}

\subsubsection{Metrics}
We adopt the three standard BIRD evaluation metrics:

\noindent\textbf{Execution Accuracy (EX)} measures exact result-set match:
\begin{equation}
    \mathrm{EX} = \frac{1}{N} \sum_{i=1}^{N} \mathbb{I}\!\left(V(Y_i) = V(\hat{Y}_i)\right)
\end{equation}

\noindent\textbf{Valid Efficiency Score (VES)} rewards faster correct queries:
\begin{equation}
    \mathrm{VES} = \frac{\sum_{i=1}^{N} \mathbb{I}(V(Y_i) = V(\hat{Y}_i)) \cdot R(\tau_i)}{\sum_{i=1}^{N} \mathbb{I}(V(Y_i) = V(\hat{Y}_i))}
\end{equation}
where $\tau_i = \tau_{Y_i} / \tau_{\hat{Y}_i}$ is the relative execution time and $R(\tau)$ awards $1.25$ for $\tau \geq 2$, $1.0$ for $1 \leq \tau < 2$, $0.75$ for $0.5 \leq \tau < 1$, and $0.50$ for $\tau < 0.5$.

\noindent\textbf{Soft F1 Score} evaluates partial correctness via token-level overlap between predicted and ground-truth result tables:
\begin{equation}
    \mathrm{F1} = \frac{2 \cdot \mathrm{Precision} \cdot \mathrm{Recall}}{\mathrm{Precision} + \mathrm{Recall}}
\end{equation}

\subsection{Analysis}

\subsubsection{Success Pattern}
Of the 8 correctly answered queries, 3 were resolved on the first attempt (zero iterations; $<1$\,s latency), confirming that well-pruned schemas and MCI metadata enable the generator to produce correct SQL without correction. The remaining 5 required 1--2 iterations through the asymmetric loop, predominantly for multi-table join queries involving \texttt{SUBSTR}-based date parsing.

\subsubsection{Failure Analysis}
The 2 failed queries (IDs~1481 and~1482) involved deeply nested cross-segment percentage calculations requiring dynamic window functions (\texttt{ROW\_NUMBER}, \texttt{PARTITION BY}). Both exhausted the $T_{\max} = 3$ iteration budget. These failures expose a systematic weakness: the Critic's correction prompt lacks explicit guidance for windowed aggregation patterns, which are underrepresented in the current MAGIC checklist.

\subsubsection{Reflector Effectiveness}
The Reflector successfully identified logical mismatches in queries where the generator confused \texttt{MIN} vs.\ \texttt{MAX} aggregation or omitted required \texttt{GROUP BY} clauses. By triggering correction \emph{before} sandbox execution, it reduced unnecessary database round-trips and lowered the overall latency for logically flawed queries.

\subsubsection{Cost Efficiency}
The average of 2.0 API calls per question validates the asymmetric design: the Critic is invoked on only $\sim$50\% of queries. Combined with the Groq API's free-tier availability for the scout model, the per-query cost is substantially lower than monolithic GPT-4 or Claude-3 setups.
