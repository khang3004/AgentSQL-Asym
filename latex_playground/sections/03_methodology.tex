\section{Method}
\label{sec:method}

\subsection{Problem Formulation}
We formulate the Text-to-SQL task over a relational database $\mathcal{D} = (\mathcal{S}, \mathcal{V})$, where $\mathcal{S} = \{T_1, T_2, \ldots, T_M\}$ is the set of $M$ tables comprising the schema and $\mathcal{V}$ denotes the stored data values. Given a natural language question $Q$, the objective is to generate the optimal executable SQL query:
\begin{equation}
    \label{eq:objective}
    \hat{y} = \arg\max_{y \in \mathcal{Y}} \; P_\theta\!\left(y \;\middle|\; Q, \mathcal{S}'_{\mathrm{enriched}}\right)
\end{equation}
where $\mathcal{S}'_{\mathrm{enriched}}$ is the dynamically constructed database context assembled by the active graph.

\subsection{Architecture Overview: The Asymmetric LangGraph State Machine}
The overall system architecture and the state transition flow of our proposed framework is illustrated in Fig.~\ref{fig:workflow}. Rather than orchestrating static sequential pipelines, we model the Text-to-SQL workflow as a unified, stateful \textbf{LangGraph State Machine} ($\mathcal{G}$). The state of the system is governed by a persistent \texttt{State} dictionary:
\begin{equation}
    \mathbf{X} = \left\langle Q, \; \mathcal{D}_{\mathrm{path}}, \; \mathcal{C}, \; \mathbf{H}, \; \{y_k\}, \; \hat{y}, \; e_i, \; t_i \right\rangle
\end{equation}
where $\mathcal{C} \in \{\textsc{Simple}, \textsc{Complex}\}$ is the query complexity, $\mathbf{H}$ is the enriched schema context, $\{y_k\}$ represents candidate SQL queries, $e_i$ is the semantic execution traceback, and $t_i$ is the iteration count.

    \centering
    \includegraphics[width=0.88\textwidth]{tikz_artifacts/agentsql_workflow.pdf}
    \caption{The AgentSQL-Asym LangGraph State Machine. For simple queries, the Adaptive Router (Node 1) directly invokes the SQL Generator (Node 3) bypassing offline schema exploration entirely. Complex queries trigger the Schema Explorer (Node 2) to build a multi-faceted metadata context (CHESS + MCI). The Resilient SQL Validator (Node 4) locally executes queries in a sandbox, looping with the Targeted Corrector (Node 6) up to 3 times on semantic errors, before the Output Aligner (Node 5) delivers the finalized query.}

\subsection{Node 1: Adaptive Router Node}
To minimise token expenditure and latency, the query enters the \textbf{Adaptive Router} node first. We deploy a fast, instruction-tuned language model $M_{\mathrm{route}}$ (\texttt{openai/gpt-oss-20b} via Groq) to classify the complexity of the natural language question $Q$:
\begin{equation}
    \mathcal{C} = \operatorname{Classifier}_{M_{\mathrm{route}}}(Q)
\end{equation}
If the query is classified as $\textsc{Simple}$ (e.g. single-table query without complex filters or joins), the graph routes \textbf{directly} to the SQL Generator (Node 3), skipping the schema exploration layer to save time. If classified as $\textsc{Complex}$, the graph triggers the Schema Explorer (Node 2).

\subsection{Node 2: Schema Explorer Node}
The \textbf{Schema Explorer} fuses semantic schema pruning and metadata profiling into a single high-fidelity context builder:

\subsubsection{CHESS Pruning}
We embed the query $Q$ using the BGE asymmetric prefix model and retrieve the Top-$k$ most relevant tables using a pre-computed inner-product FAISS index:
\begin{equation}
    \mathcal{S}' = \operatorname{Top\text{-}k}_{T_j \in \mathcal{S}} \left\langle \mathbf{e}_Q, \; \mathbf{e}_{T_j} \right\rangle
\end{equation}

\subsubsection{MCI-SQL Enrichment}
For each retrieved table $T \in \mathcal{S}'$, the node performs local SQLite introspection queries to build a profile context:
\begin{itemize}
    \item \textbf{Numeric columns}: Extracts absolute $\min(c)$ and $\max(c)$ range limits.
    \item \textbf{Text columns}: Obtains $n_s = 3$ random non-null literal sample values.
    \item \textbf{Cardinality profiling}: Infers key relationships by computing unique ratios:
    \begin{equation}
        \operatorname{Card}(c) = \frac{|\operatorname{DISTINCT}(c)|}{|\operatorname{COUNT}(*)|}
    \end{equation}
\end{itemize}
The result is consolidated into the enriched context string $\mathcal{S}'_{\mathrm{enriched}}$, which minimizes schema noise from other tables.

\subsection{Node 3: SQL Generator Node}
The \textbf{SQL Generator Node} utilizes the premium \texttt{google/gemma-4-31b-it} model to synthesize two parallel candidate queries:
\begin{enumerate}
    \item \textbf{Candidate 1 ($y_1$)}: Generated using the standard DDL schema representation.
    \item \textbf{Candidate 2 ($y_2$)}: Generated using a lightweight Markdown-formatted schema description.
\end{enumerate}
Both candidates are instantly run inside a local SQLite execution sandbox. The node evaluates sandbox feedback ($e_1, e_2$) and selects the best candidate (the one executing successfully, or the one with fewer syntactic errors) as the starting candidate $y_0$.

\subsection{Node 4: Resilient SQL Validator Node}
The \textbf{SQL Validator} executes the active candidate SQL query $y_i$ in the local sandbox and evaluates its semantic state using a three-tier taxonomy (Table~\ref{tab:semantic_states}):

\begin{table}[t]
    \centering
    \caption{Three-tier Semantic State Evaluation taxonomy.}
    \label{tab:semantic_states}
    \footnotesize
    \setlength{\tabcolsep}{3pt}
    \begin{tabularx}{\columnwidth}{@{}l>{\raggedright\arraybackslash}X>{\raggedright\arraybackslash}X@{}}
        \toprule
        \textbf{State}       & \textbf{Trigger}                  & \textbf{Description}                 \\
        \midrule
        \textsc{SyntaxError} & SQLite \texttt{OperationalError}  & Compilation or table/column mismatches\\
        \textsc{EmptyResult} & $|\mathrm{rows}| = 0$             & Executed but returned empty results  \\
        \textsc{NullResult}  & $\forall$ cells $= \texttt{NULL}$ & Empty projection due to faulty JOIN  \\
        \textsc{Success}     & Non-empty, non-null rows          & Validated execution success           \\
        \bottomrule
    \end{tabularx}
\end{table}

If the state is evaluated as \textsc{Success}, the graph immediately exits the loop and routes to Node 5 (Output Aligner). If any other state is triggered, the query is routed to Node 6 (Targeted Corrector).

\subsection{Node 6: Targeted Resilient Corrector Node}
When a query fails validation, the \textbf{Targeted Corrector} ($M_{\mathrm{correct}}$, using the high-capacity \texttt{openai/gpt-oss-120b} via Groq) is invoked. The corrector receives:
\begin{equation}
    y_{i+1} = M_{\mathrm{correct}}(y_i, \; e_i, \; \mathcal{S}'_{\mathrm{enriched}})
\end{equation}
where $e_i$ is the exact compiler traceback or logical mismatch report. The corrected query $y_{i+1}$ is returned to Node 4 (SQL Validator) for re-execution. This feedback loop runs up to $T_{\max} = 3$ iterations before falling back to a safe fallback selection.

\subsection{Node 5: Output Aligner Node}
Once validation succeeds, the \textbf{Output Aligner} ($M_{\mathrm{align}}$, using \texttt{openai/gpt-oss-20b} via Groq) standardizes the SELECT projection:
\begin{equation}
    \hat{y} = M_{\mathrm{align}}(y_{\mathrm{valid}}, \; Q)
\end{equation}
It ensures table alias conventions, keyword casings, and sorting orders are perfectly aligned with the ground truth patterns expected for BIRD, outputting the final executable query $\hat{y}$.
